# Testing

Where each kind of test lives, how to run it, and what stops a change that breaks it. Each area has its own `make` target, and `make test-matrix` runs them all. The gates named below are the jobs in [`.github/workflows-export/gates.yml`](../.github/workflows-export/gates.yml), which this repository does not run itself; [CONTRIBUTING.md](../CONTRIBUTING.md) says how to enable them.

## The test areas

| Area | What it covers | Run it | What gates it | Where a new test goes |
|---|---|---|---|---|
| Seed checks | `scripts/check-seed-sql.py`, and the committed seed SQL it checks | `make test-seed-checks` | The Test gate: `make ci-test` runs the checker's tests, and `make db-seed-check` runs the checks against the committed seed | `scripts/test_check_seed_sql.py` |
| Browser flows | The bridge in a real browser, against the built app and a seeded Postgres. Today that is a smoke test that the layer cake draws the seeded catalog, and a check that a focused chip and a focused tab show the focus outline; the filter, search and control flows come next | `make test-browser` | The Browser job, on every pull request that is not a draft and on every push to `standard` | `app/e2e/`, named `*.spec.ts` |
| Accessibility scan | frostfall (axe-core) over the bridge's page states, against the same app as the browser flows: WCAG 2.2 A and AA, failing on a violation rated serious or worse that the baseline does not list | `make test-a11y`, or as part of `make test-browser` | The Browser job | A state in `app/e2e/frostfall/frostfall.yml` |
| API surface | The tRPC setup and its client wiring (`src/server/api/trpc.ts`, `src/trpc/`), the auth wiring (`src/server/auth/`), the database client and the route handlers | `make test-api` | The Test gate: `make ci-test` runs them, with the coverage floor | A `__tests__/` folder beside the module |
| Seed pipeline | The generators' offline build steps, each run into a scratch directory and compared with the committed seed and reports byte for byte, and the seed loader, its two entry points and its helpers with `pg` mocked. The loader also runs against a real Postgres, which checks that every row the seed inserts arrives | `make test-pipeline`; the Postgres run is in `make test-integration` | The Test gate: `make ci-test` runs them, with the coverage floor. The Postgres run is in the Integration job | A `__tests__/` folder beside the generator or module; a Postgres test is `*.integration.test.ts` |
| Scripts | The shell scripts under `scripts/`, run through bash with `aws`, `docker`, `ps`, `sleep`, `terraform` and `trivy` stubbed, and the recovery's row-count check against the committed seed | `make test-scripts` | The Test gate: `make ci-test` runs them | `scripts/test_shell_scripts.py` |
| Image scans | The base images the `Dockerfile` pins, and the runner image built on them, against the policy in `trivy.yaml`. See [Image scans](#image-scans) | `make scan-base` (seconds, no build); `make container-scan` (a full build) | The CVE scan gate runs `make container-scan`, with a `dhi.io` login. `make pre-push`, and `make test-integration` run by hand, run `scan-base`; `make ecr-build-push` runs the full scan before an image ships | A finding assessed as not affecting the image: a statement in `security/vex.openvex.json`, with its evidence |

The gates do not run `make test-matrix`. The Test gate runs `make ci-test` and `make db-seed-check`, which between them run every area above except the browser tests, which run in the Browser job. A new area's tests must run through one of those, or through a gate of their own, before the area counts as gated; adding its target to `test-matrix` alone gates nothing.

A seed check needs three tests: clean input that passes, broken input that the check reports, and a case in `test_main_exits_one_on_each_defect` proving the script exits 1 on that defect. A check whose finding is printed but never fails the run gates nothing.

A script test runs the script for real, with every command that reaches outside the repository replaced by a stub on `PATH` that records its calls and answers from fixtures. Assert what the script would have run, especially that a call which changes something names only what it should: `dr-restore-test.sh` and `db-recover.sh` may read the live database but must only change the copy they restore. `local-env.sh stop` is not covered, and of `status` only the listeners it lists are; `stop` signals processes with the shell's own `kill`, which a stub cannot intercept.

An API test mocks what lies outside the app (Auth.js, Prisma, Next's request headers) and runs the app's own code: the route handler test sends requests through the real handler, context, middleware and error formatter, against a small router built from the real procedure builders. Modules that do their work on import (the auth configuration, the database client) are loaded fresh per case with `vi.resetModules()`. Mock call history is cleared before each test, so work done on import is recorded in plain arrays rather than read from a mock afterwards.

A browser test runs against what ships: `make test-browser` builds the standalone server with `next build`, starts a throwaway Postgres migrated and seeded by the integration harness in `app/src/test/db/`, and starts a browser in Microsoft's Playwright image, pinned by digest in `app/e2e/global-setup.ts`. The browser sits in that container and reaches the app at `host.docker.internal`, so `page` uses the configured `baseURL`; code running in the test process itself reaches the app at `process.env.E2E_HOST_URL`. Find elements by role, label or text rather than by class, so a change of styling doesn't break a flow. To move to a new Playwright release, change `@playwright/test` in `app/package.json` and `BROWSER_IMAGE` together; the setup refuses to start when their versions differ.

The accessibility scan is `app/e2e/a11y.spec.ts`. It runs [frostfall](https://github.com/aquia-inc/frostfall) over the page states listed in `app/e2e/frostfall/frostfall.yml`, in a second container from the same Playwright image, on that image's Chromium. `make _install-frostfall`, which the browser targets run first, fetches frostfall's Linux build for Docker's architecture and checks the download against the sha256 pinned in the Makefile and against the release's `checksums.txt`. The binary is kept in `app/.frostfall/<version>/`, and its own pinned sha256 is checked before every run; a binary that no longer matches is fetched and checked again. To move to a new frostfall release, change `FROSTFALL_VERSION`, both `FROSTFALL_SHA256_*` values and both `FROSTFALL_BIN_SHA256_*` values together, then run `make a11y-baseline`, since a new axe-core version can find different things.

- **Reading a failure.** The test prints frostfall's output: each new violation with its rule, page state, element and a link to the rule's fix. frostfall exits 1 for a new violation rated serious or worse (a new moderate or minor one is reported but passes), 2 for a config error, and 3 when it could not reach a page or a step's element, which is a broken state rather than a violation. The HTML report, with a screenshot of each new violation, is in `app/frostfall-report/` locally and in the Browser job's `frostfall-report` artifact in CI.
- **Adding a page state.** Add a test to `frostfall.yml` with a stable `id`, since the id is part of every baseline entry. Wait for an element that only exists once the state is ready, not a fixed delay, and that belongs to the new state rather than one any page has: after a click the router keeps the old view on screen until the server answers, which is why the modal states wait on the modal's `data-control-id`. Scope a scan of something drawn over the cake (the modal, the search results) to that element, so the cake's violations are counted once. frostfall finds elements by CSS only; where a role, label or `href` won't pick out the element, add a `data-` attribute to it, as the modal's cross-reference buttons have `data-control-ref`. The search state's entries name the controls that match its query, so a seed change that alters those results shows up as new and stale entries; rewrite the baseline for it in the same PR.
- **The baseline.** `app/e2e/frostfall/baseline.json` lists the violations the scan accepts for now, each with a `note` saying in words what fixes it or why it stands. It is empty today: the light-mode color tokens fixed the contrast violations the scan first found. A note carries no issue link or number: the vocabulary gate refuses this repository's URL under `app/`, and Standard's export refuses any citation, since it would point at nothing in the exported repository. A violation in it does not fail the scan; a new one does, and so does an entry the scan no longer finds. A second test in the spec fails on an entry whose state is no longer in `frostfall.yml`, which frostfall never reports as stale, on an entry whose note is shorter than 20 characters, and on a note that cites an issue. After fixing one, run `make a11y-baseline` and commit the shorter file. `make a11y-baseline` accepts whatever the scan finds, new violations included, so read its diff: an entry that changed only because its element's classes did needs its note again, and a new entry needs a reviewer to agree it can wait, with a note saying what fixes it. Never add one to get a build green.
- **The dark theme.** frostfall cannot emulate a dark color scheme, so each state has a dark twin, its id ending in `-dark`. The twin chooses Dark in the Theme control, then opens its page again, so it renders dark from the start, and runs the same steps and scopes. A new state needs its twin too.
- **Not covered.** Automated rules check about a third to half of WCAG; keyboard and screen-reader checks stay manual. frostfall reads only axe's violations, so a check axe cannot decide, such as contrast over a background image, a gradient or the modal's blurred backdrop, is reported as incomplete by axe and neither fails the scan nor appears in its report. Those need a manual check.

`07-control-parameters.sql` is intentionally empty for NIST SP 800-53, which assigns no parameter values, so on the committed seed the parameter check can only pass. Its tests run it against synthetic values.

## Image scans

`trivy.yaml` at the repository root is the scan policy, and every scan reads it: `make container-scan`, the CVE gate in `make ecr-build-push`, `make image-scan` and `make scan-base`. It fails on a HIGH or CRITICAL vulnerability that has a fixed version, passes one with no fix yet, and prints a Suppressed Vulnerabilities table beside the findings, naming each finding the VEX file suppressed, its justification and its source. A change to the policy is a change to that one file.

`security/vex.openvex.json` is an OpenVEX document of vulnerabilities assessed as not affecting the image, authored by the team `SECURITY.md` names. Each statement names one package by the PURL Trivy reports for it, so it is specific to a version (and, for an OS package, an architecture) and cannot suppress the same CVE in a later package, and its `impact_statement` carries the evidence. A statement is a decision and lands through review like code. It is removed once no deployed image carries the package version it names.

`make scan-base` scans every pinned base without a build, and each one is a gate: the build stages' base as well as the runner's. [`docs/scripts/scan-base.md`](scripts/scan-base.md) has the detail.

### CVE-2026-107891: not reachable in this image

An image built on the earlier base digests fails the scan on CVE-2026-107891, an integer overflow in musl's `regcomp` when it compiles an untrusted regular expression (CVSS 8.1, AV:N/AC:H), published 2026-11-05 against musl 1.2.5-r12 and fixed in 1.2.5-r13. Nothing in the image calls `regcomp`. Of the 10 ELF files in the runner image (node, the sharp and libvips modules, next-swc, esbuild, the Prisma schema engine, libgcc_s, libstdc++, `/usr/bin/env` and the musl loader), none imports it: `llvm-nm -D --undefined-only` lists 584 imports for node and `regcomp` is not among them, esbuild is a static Go binary with no imports at all, and the loader is where `regcomp` is defined. JavaScript regular expressions run on V8's own engine, not musl's. The VEX file records it as `not_affected`, `vulnerable_code_not_in_execute_path`, for `pkg:apk/alpine/musl@1.2.5-r12?arch=aarch64&distro=3.22`.

Both base images now pin digests that carry musl 1.2.5-r13, so an image built on them has nothing for the statement to suppress. It stays while an environment runs an image built on 1.2.5-r12, such as v0.1.14: without it, `make image-scan` of that image fails on a finding already assessed. Remove it once no environment runs one.

### The npm CLI in the build base: not run, not shipped

The `-dev` base that the build stages start from (`base`, `deps`, `builder`, `prod-deps` and `development`) carries the npm CLI bundled with Node, under `/opt/nodejs/node-v24.22.2/lib/node_modules/npm`. Two packages bundled inside it have six HIGH findings with a fix: `brace-expansion` 5.0.9 (CVE-2026-102276, CVE-2026-102278) and `undici` 6.28.0 (CVE-2026-19534, CVE-2026-87018, CVE-2026-109383, CVE-2026-109869). The fix is a newer npm in the base image. On 2026-11-09 the tag's newest digest still bundled npm 11.21.2 with the same two versions.

Nothing runs that code, and none of it ships:

- No build step runs npm, npx, corepack or node-gyp. `yarn` in that base is a standalone Yarn 1 under `/opt/yarn`, which hands off to the Yarn 4 release committed under `app/.yarn/releases`. Install scripts run only for Prisma's two packages and the app's own `postinstall` (`prisma generate`, then husky).
- A copy of the `Dockerfile` that deletes `/opt/nodejs/node-v24.22.2/lib/node_modules` from the base, and puts stubs that record any call in place of `npm`, `npx`, `corepack`, `pnpm` and `node-gyp`, builds the `runner` and `development` targets with no call recorded in any stage.
- The runner stage starts from the runtime base, which carries no npm (Trivy finds no Node.js package in it), and copies only what the build stages produce under `/app`, and the RDS CA bundle.

The VEX file records the six as `not_affected`, `vulnerable_code_not_in_execute_path`, for `pkg:npm/brace-expansion@5.0.9` and `pkg:npm/undici@6.28.0` inside the build stages' base only: each statement's product is that base at its pinned digest, `pkg:oci/node@sha256:6281bb92…?repository_url=dhi.io/node`, with the npm package as a subcomponent. So a statement suppresses nothing in any other image: a scan of the runner, or of the app's own dependencies if they ever resolved to one of those versions, fails on it as on any other finding. Scanning the `-dev` tag's next digest, which bundles the same npm, reports all six. When `make refresh-image-digests` moves the `-dev` pin, the statements stop matching and `make scan-base` fails until each statement's product moves to the new digest or the statement goes. Remove the statements once the `-dev` pin carries an npm whose bundled packages are fixed.

These six statements are an assessment, open to rejection in review. The alternatives are:

- **A hardened base whose bundled npm carries the fixes.** Move the `-dev` pin to it once one is published, and drop the statements.
- **Let `make scan-base` fail on the build base until then.** Drop the statements. `make pre-push` then fails on the six findings. `make container-scan`, which the CVE scan gate in `.github/workflows-export/gates.yml` runs, and the scan in `make ecr-build-push` scan the runner, which has no npm, so they pass either way.

This change takes neither: it records the six findings as not affecting the image, on the evidence above. Either alternative begins by reverting the commit that adds the statements.

### Options considered and not adopted

- **Amazon Inspector enhanced scanning for ECR.** It rescans the images already in ECR whenever a new CVE is published, which is how a CVE published after an image was built would surface without anyone running a scan again. Not adopted here: it is switched on for the whole registry, an account decision rather than a change to this repository, and it is billed for each image scanned and rescanned.
- **A scheduled scan of the pinned base digests**, beside the weekly base-image and RDS CA bundle gates in `.github/workflows-export/gates.yml`. It would find a new CVE against the pins between releases. Not adopted: this repository runs no CI of its own, and a runner pulls the Docker Hardened Images only with a `dhi.io` login. A fork that enables the gates with that login can schedule `make scan-base` beside them.

## The suites underneath

The areas above sit on the same suites everything else uses.

| Suite | Run it | What gates it | Where a new test goes |
|---|---|---|---|
| Unit (Vitest, mocked database) | `make ci-test-js` | The Test gate, with the coverage floor | A `__tests__/` folder beside the code, named `*.test.ts` or `*.test.tsx` |
| Integration (Vitest, real Postgres in a throwaway container) | `make test-integration` | The Integration job, on every pull request that is not a draft and on every push to `standard` | `*.integration.test.ts`, using the harness in `app/src/test/db/` |
| Browser (Playwright, the built app, a real Postgres and a browser in a pinned container) | `make test-browser` | The Browser job, on every pull request that is not a draft and on every push to `standard` | `app/e2e/`, named `*.spec.ts` |
| pytest (the Python checkers and the shell scripts) | `make ci-test-python` | The Test gate | `scripts/test_<script>.py`, added to `PYTEST_FILES` in the Makefile, which names each suite |

## Coverage

The coverage floors in `app/vitest.config.ts` (95% lines and statements, 90% functions, 88% branches) are measured once, over the whole unit suite, in `make ci-test`. They count every source file under `app/src`, `app/prisma` and `app/scripts`, whether a test imports it or not, so a module no test reaches shows as uncovered instead of missing from the report. An area's own target runs without them, because one area alone cannot meet a floor set for the whole suite. Never lower a floor to get a build green: cover the branch, or exclude the file with its reason written beside the exclusion.

## The vocabulary gate

`make ci-test` also sweeps every file this repository ships, tests and fixtures included, for the vocabulary of other catalogs. The terms are in `app/src/config/catalog-vocabulary.ts`. A test fixture that needs a control identifier uses a NIST one.
